# Formatting and linting

## Requirements

Every formatter or linter must be usable in four ways:

| Caller         | Files                | Mode                         |
| -------------- | -------------------- | ---------------------------- |
| Manual         | All                  | Check or fix                 |
| Git pre-commit | Staged files         | Check (or fix and re-stage)  |
| CI             | All                  | Check only, never writes     |
| Agent hook     | The file just edited | Fix, then report what's left |

So each one gets a single entry point with a check mode and a fix mode. It takes
an optional list of files and runs on everything when given none. Each of the
four callers is then a thin wrapper around that entry point.

Adding a formatter or linter for a language must not change how existing tools
are called. Each repository configures only the languages it uses itself:
project-specific language tools belong in the project repository, while
`WJ44/harness` only includes baseline tools and languages used in the harness.
Only open an issue on `WJ44/harness` if the harness plumbing needs changes to
support a language or if a tool choice should be recorded as a shared default.

## Formatting

Prettier is the baseline formatter, because most projects will want it and it
covers many file types.

Formatters are run via `lefthook`:

```bash
lefthook run format                        # fix all files
lefthook run format-check                  # check all files, write nothing
lefthook run format --file path/to/file    # fix specific files (repeatable)
```

The git pre-commit hook runs `format` on the staged files and re-stages them.

"All files" means files tracked by git, so new files are skipped until they're
added. `--file` works on any file, so agent hooks must pass the edited file with
`--file`: a file the agent just created isn't tracked yet.

| File                    | Role                                                         |
| ----------------------- | ------------------------------------------------------------ |
| `.editorconfig`         | Settings every tool reads, where they differ from defaults   |
| `.gitattributes`        | Makes git keep line endings, also on Windows checkouts       |
| `.prettierrc.json`      | Prettier-only options (`proseWrap: "always"`)                |
| `.prettierignore`       | File types another formatter owns, and generated files       |
| `lefthook.yml`          | Maps files to tools; format, format-check, lint, lint-check  |
| `mise.toml`             | Pinned versions of tools (Prettier, shfmt, ruff, etc.)       |
| `mise.lock`, `.mise/`   | Checksums and dependency locks, generated by mise            |
| `setup-user.sh`         | Installs mise and the tools; registers the hook              |
| `hooks/post-edit`       | Post-edit agent hook running format and lint on edited files |
| `.claude/settings.json` | Claude Code PostToolUse hook configuration                   |
| `.agents/hooks.json`    | Antigravity PostToolUse and PostInvocation hook config       |

Tools:

- **Prettier** gets every file and skips the ones it doesn't handle
  (`--ignore-unknown`).
- **shfmt** formats shell. `shfmt --find` picks out shell files by extension
  (`.sh`, `.bash`…) or shebang, so a script without either isn't formatted: give
  sourced shell files a shebang.
- **tombi** formats TOML (`*.toml`, by `glob`: it parses every file it's given
  as TOML). It fetches JSON Schemas from SchemaStore (cached for a day) to
  format and sort keys per file type, so it needs network access to
  `www.schemastore.org`.
- **Node** runs Prettier and other npm-packaged tools pinned in `mise.toml`.

### Adding a formatter

1. Pin it in `mise.toml` (`mise use <tool>@<version>`), which also updates
   `mise.lock`. npm tools use the `npm:` backend, so they stay out of the
   project's own `package.json`.
2. Add a job to `format` and `format-check` in `lefthook.yml` (pre-commit runs
   `format`, so it needs no change). Prefer the tool's own way of picking out
   its files (like Prettier's `--ignore-unknown` or shfmt's `--find`); otherwise
   give the job a `glob`. Commands with a pipe start with `set -o pipefail`, so
   a failure early in the pipe isn't hidden.
3. If it takes over file types Prettier also formats, add them to
   `.prettierignore`, so every file has exactly one formatter.
4. Leave settings at the tool's defaults where they're fine. When custom
   settings are needed, put them in `.editorconfig` if the tool supports it; use
   a tool-specific config file only for settings `.editorconfig` cannot express.
5. If the first run reformats existing files, commit that on its own, so
   reviewers can tell the tooling change from the reformat.

## Linting

Linting checks code quality, static analysis, and potential bugs.

```bash
lefthook run lint                          # fix all files (where supported)
lefthook run lint-check                    # check all files, write nothing
lefthook run lint --file path/to/file      # fix specific files (repeatable)
lefthook run lint-check --file path/to/file# check specific files (repeatable)
```

The git pre-commit hook runs `lint-check` on the staged files after `format`.

Tools:

- **shellcheck** lints shell scripts. It finds files via `shfmt --find=0`, so
  any file with a shell shebang or extension is checked. Shellcheck is
  check-only.
- **Ruff** lints Python (`*.py`). It is fast and replaces flake8, isort, and
  other Python linters. In fix mode (`lint`), `ruff check --fix` automatically
  fixes autofixable lint violations.

### Adding a linter

1. Pin it in `mise.toml` (`mise use <tool>@<version>`), which also updates
   `mise.lock`.
2. Add a job to `lint` and `lint-check` in `lefthook.yml`. Prefer the tool's own
   way of picking out its files; otherwise give the job a `glob`. Commands with
   a pipe start with `set -o pipefail`, so a failure early in the pipe isn't
   hidden.
3. Leave settings at the tool's defaults where they're fine. When custom
   settings are needed, put them in `.editorconfig` if the tool supports it; use
   a tool-specific config file only for settings `.editorconfig` cannot express.
4. If existing files have lint violations, fix them and commit that on its own,
   so reviewers can tell the tooling change from code changes.

## Agent hooks

Post-edit agent hooks run automatically after an agent modifies or writes a
file:

1. Claude Code (`.claude/settings.json`) triggers `hooks/post-edit` on
   `PostToolUse` for `Edit|Write|MultiEdit`.
2. Antigravity (`.agents/hooks.json`) triggers `hooks/post-edit` on
   `PostToolUse` for `write_file|edit_file` and on `PostInvocation`.

`hooks/post-edit` runs:

```bash
lefthook run format --no-auto-install --file <path>
lefthook run lint --no-auto-install --file <path>
```

- `--file` ensures untracked files newly created by agents are formatted and
  linted immediately.
- Files outside the repository (e.g. agent artifacts, scratchpads) and deleted
  files are ignored.
- Unfixable lint errors are surfaced back to the calling agent so it can
  course-correct immediately without waiting for pre-commit checks or CI.
